## Blockers (found by a live run, Chainlink #1127)

One remains, and it belongs to the product rather than to the harnesses.

| Blocker | Effect | Status |
| --- | --- | --- |
| #1147: `init` propagated `CODEX_HOME` *after* creating the session's first window | When a tmux server was already running, the window `init` renames to `Server` kept the existing server's captured `CODEX_HOME`. The session environment then read correctly, so a `tmux show-environment` check passed, while the server and every agent it spawns resolved a different Codex home and no hook trust was seeded. | **Fixed in the product.** tmux snapshots a pane's environment when it spawns the pane's process and never re-reads it, so a value written after `new-session` reaches only the windows created later; the window `new-session` already created falls back to the tmux server's global environment, which the server captured from whichever process started it. `CODEX_HOME` now travels into `new-session` itself as `-e CODEX_HOME=<path>`, which tmux merges into the session environment *before* it spawns the first window, so the `Server` pane is born with it and every window created later inherits it from the session. `init` then reads the spawned pane's own `/proc/<pid>/environ` and refuses to start when it disagrees, so a session that reads back correctly while its pane runs on another home cannot pass silently again. The harnesses keep `e2e_python_tl_isolate_tmux_server` (`TMUX_TMPDIR` under the work dir) as well: it is defence in depth for a run's own tmux server, not the thing that made the worker see the right home. Set `E2E_PYTHON_TL_TMUX_ISOLATION=0` to run against the host's shared server. |
| #1149: the fixtures and the `exomonad new` scaffold provision a model the account cannot run | The worker gets `400 invalid_request_error` on its first inference and never makes a tool call, so every live Codex scenario stalls for the validator's whole budget and reads as a messaging failure. | **Fixed in both the fixtures and the shipped scaffold.** The model is resolved from the host Codex config, `gpt-luna` is refused outright, and one throwaway `codex exec` proves the account can run the resolved model before `init` starts -- which turns a 600s ambiguous stall into a 5s message naming the model, and surfaces the policy/capability-map mismatch within ninety seconds. Confirmed live on a fresh host: the probe reports `OK: account can run model gpt-5.6-luna` and both fixture files are written with the resolved `codex/gpt-5.6-luna` key. The scaffold side (`rust/exomonad/src/codex_model.rs`) resolves the same way: `EXOMONAD_CODEX_MODEL`, else the top-level `model` in the Codex config, with no built-in default -- so `exomonad new` refuses before writing anything rather than provisioning a worker that cannot take a turn, and its harness-policy and capability templates take the resolved harness instead of a literal. `init`'s capability backfill now rates the harnesses the existing policy names rather than one hard-coded model. |
| #1148: the controller quarantines the slice's own dispatch confirmation | The slice never leaves `spawned` and the run stays at `tl_running`, so a worker that did its whole job correctly still does not finish. | **Open, and the only blocker.** The action journal ends with `tl.dispatch_event_rejected` (`integrity_conflict` / `intent_mismatch`), and `event-quarantine.json` holds the `agent.spawned` event with `run_id` a UUID where the controller has the literal `root`, and `agent_id` `root` where it expects the slice. The worker is correct: its `notify_parent` returned `success`, and the run's logs hold `message.delivery` for `recipient: root` by both `Tmux` and `agent_inbox_tmux`. The premise this issue was first filed under -- a worker that never calls `notify_parent` -- was wrong twice over and is corrected here. **Reproduced independently by the `python-tl-worker-notify` migration** (2026-09-30, work dir `python-tl-worker-notify.kT0YrtMB`, `run_id` `949d5daf-be5c-4f2a-9307-107225592541`), on a different host and a different scenario from the ones that filed it, which is what makes it a product defect rather than a fixture artefact. | #1150: `serve` leaves a stale `server.sock` behind when it loses the TCP bind, and `init` then waits out its full budget on a dead socket | `init` exits 1 before it reaches the controller, so the run never dispatches and the validator never starts. | **Both product defects fixed.** The cause was confirmed on 2026-09-30 and is not host-dependent: a run left its `exomonad serve` holding the default webhook port `0.0.0.0:7433`, the fixture sets no `port`, so a later `serve` bound the UDS, then failed `Failed to bind TCP listener 0.0.0.0:7433` with `Address already in use` and exited 1 -- **leaving `server.sock` on disk**. `wait_for_server_socket` passed its "socket exists" check and then polled `is_healthy` against a socket with no listener, so a fast failure was reported as `Server socket exists but health check failed after 30s`. The two defects behind that are now closed in `serve` and `init`. **The socket is reaped on every exit path** (`rust/exomonad/src/serve.rs`): `serve` binds the Unix socket before the public TCP listener, and its cleanup block sat after `try_join!`, so the bind-failure path skipped it entirely. A `ServerArtifacts` guard armed right after the pid record is written reclaims the socket on every exit, and only reclaims what this process owns -- a successor server's socket survives. **The wait now stops when the server is provably gone** (`rust/exomonad/src/init.rs`): a recorded pid that has exited, or a socket nothing is listening on. The socket is reclaimed on every exit path but the pid record is deliberately left behind as a tombstone -- a record that exists only while the server is alive disappears inside one poll interval of a server that dies quickly, leaving `init` no way to tell that apart from one that has not started yet, and no choice but to wait out its budget. `init` also latches the pid it observes so a record it saw live and then found dead is decisive. Failures carry the Server window's captured output, which is where `serve`'s stderr actually lands. An absent or unreadable pid record still proves nothing and is awaited, as is a socket that is up but not yet answering `/health` -- real servers take seconds to load WASM and the budget covers that. **Verified on this host against the exact contended-port failure:** `init` now exits in ~13s instead of 30s and reports `exited before the server became healthy` together with `Address already in use (os error 98)` from the pane. The remaining ~13s is `serve`'s own WASM load before it reaches the bind; `init` stops within one poll of the exit, not at its own deadline. The healthy path still reaches Watcher and TL windows, and SIGTERM reclaims the socket. New tests cover the outcomes, including a server that binds, exits, and reclaims its socket while leaving the record behind. **What this does not change:** the port collision itself is real, so `chainlink-codex` keeps `port = 0` and any fixture sharing a host still needs port discipline; a leftover `serve` from an earlier run is still reaped only by the session teardown that owns it; and a stale pid record now survives its server, which the next `init` clears before starting anything.

The tmux isolation is on by default and stays there. An earlier revision had
reverted it, believing it broke the server's socket health check. That belief
was wrong, and the check has since separated the two claims:

* The isolation call really was inside `cleanup()`, so it only took effect at
  teardown. Moved to top level it works, and it gives the worker a run's own tmux
  server, whose captured `CODEX_HOME` is the run's -- proven live for all three
  scenarios. Since #1147 the run's Codex home reaches that server's first window
  through `new-session -e` even when the server is the host's, so the isolation
  no longer carries the correctness on its own.
* The socket health check that still failed was never the isolation's doing.
  `chainlink-codex` failed it with `E2E_PYTHON_TL_TMUX_ISOLATION=0`, four times
  in four, and the cause was the fixture contending for the default webhook port
  with a server an earlier run had left behind (#1150, above). With `port = 0`
  set, the same scenario clears the check and dispatches. That contention no
  longer has a stale socket behind it: `serve` reaps its socket on the way out
  and keeps its pid record, so the collision now surfaces as the bind error
  itself.

`tests/e2e/python-tl-controller/test_isolation_contract.py` pins the placement
either way.

Two harness defects were shared by all three migrated validators, and are now
fixed in two of them.

The bracketed-marker grep. Each waits for a `[...]` marker in `.exo/logs` by
passing it to `grep` as a pattern, but the brackets open a bracket expression
whose `-` characters are ranges, so GNU grep rejects the pattern with `Invalid
range end` and exits 2 -- the probe can never succeed, and `wait_for` reports a
timeout for a marker the worker did write. `chainlink-codex` and
`python-tl-worker-notify` use `grep -RF` now and are pinned by
`test_contract.py::MARKER_FIXED`; `codex-messaging` still carries it as
`PENDING_MARKER_FIX` (#1152). The `python-tl-worker-notify` live run found this
one the hard way: its delivery assertion passed the moment the fix landed, on a
log that had been sitting there holding the marker all along.

The `set -e` abort. `validate.sh` runs under `set -euo pipefail` and calls its
assertion helpers as bare statements, so a helper returning 1 on failure exited
the script at the *first* failed assertion -- skipping every later assertion and
never writing `$RESULT_FILE`. `run.sh` then reported `validator wrote no result
file`, the opposite of what happened: real recorded failures, all discarded.
`chainlink-codex` and `python-tl-worker-notify` return 0 and let the failure count
decide, which is what `run.sh` keys on; `codex-messaging` still carries it as
`PENDING_SET_E_FIX` (#1152).

A third defect, found only by the `python-tl-worker-notify` live run and now
pinned for every migrated scenario by
`test_contract.py::test_no_wait_for_probe_is_an_unreachable_shell_function`: a
`wait_for` probe must be reachable from the shell that runs it. `wait_for`
evaluates its probe with `bash -c`, which starts a fresh shell that inherits
exported variables but *not* unexported shell functions. Handing it the bare name
of a function defined in the same file can therefore only ever exit 127 with
`command not found`, so the assertion burns its entire budget while the property
it checks is demonstrably true -- which is what
`notification reached the controller window` did for 600s while the same run's
logs held two successful deliveries. The probe is now a `--assert-window-marker`
re-entry point invoked as `bash "$0" ...`, the idiom `chainlink-codex` already
used for its own subshell assertions.

The backtick-in-heredoc defect below is fixed in `chainlink-codex` only. All three
harnesses write `.exo/config.toml` through an **unquoted** heredoc, so a backtick
is a command substitution. The rationale comment for `port = 0` was written with
backticks around the words it mentioned, and the words were silently executed and
deleted on the way into the file -- the preserved `chainlink-codex.WsMhnhZk` run's
`config.toml` reads `#  takes an ephemeral port...`, with every backticked word
gone and `init` resolved to systemd along the way. A backticked word that prints
anything would have its output spliced un-commented into the middle of the file
the controller parses. `chainlink-codex` now writes the words plainly, and
`test_inventory.py::test_chainlink_codex_config_heredoc_has_no_command_substitutions`
pins it against *unescaped* backticks (an escaped one is the documented escape
hatch and renders correctly). `codex-messaging` carries the identical defect in
its own companion comment -- its preserved `q8sxs0Ek` `config.toml` reads
`#  is a required field of  (a plain  with no` -- and is owned by #1152;
`python-tl-worker-notify` has no backticks and is unaffected.

All three migrated scenarios now treat a missing or failing validator result as
a failure. They previously fell back to `exomonad init`'s exit status, and
`init` exits 0 as soon as it attaches the session -- so a 2026-09-30 run that
failed three assertions and wrote no verdict still exited 0.

## Codex Hooks Feedback

- Hook trust is now asserted where it is written. The migrated Codex scenarios check the generated child config for the three hook commands, and the run's isolated `CODEX_HOME` for one `[hooks.state."<child config>:<event>:0:0"]` entry with a `trusted_hash` per event plus `[projects."<agent dir>"] trust_level = "trusted"`. That is the same property the `3 hooks need review before they can run` warning is about. The retired `# BEGIN EXOMONAD CODEX HOOKS` block is asserted **absent**: its writer was removed in 8934378f (#210) and `trust_codex_project` strips it on every write.
- A stale project-root `.codex/config.toml` is the other half of that gate: Codex applies project config to every session opened in the project, so a leftover one from the Codex root-TL era silently re-enables the retired Root TL protocol for any operator session. The migrated validators assert that normal Python-controller startup generates none, at the project root or under the root agent identity. A historical residue report is tracked separately (chainlink #1145).
- The hook denial path is working: the validator's Codex-shaped `gh auth status` payload received a deny response with `permissionDecision = deny`.
- Reviewer MCP scope is now explicit: reviewer-role `tools/list` includes `approve_pr`, `request_changes`, `post_review_comment`, and `notify_parent`; `just test-wasm-integration` covers this.
- The Codex scenarios must remain local-only: unset Forgejo auth and keep Forgejo-backed PR integration in a separate E2E.
